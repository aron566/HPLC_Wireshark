## 0. 关键方法论发现（本次最重要的一条）

**PDF 文本流不表达合并单元格（rowspan/colspan）。**

国网 HDC2.0 规范的表格大量使用**垂直合并单元格**表达「一个字节号跨两行」。
文本流（`page.get_text()`）会把它拍平成断裂序列，例如表92 输出为：

```
代理TEI 6 0-7 12 比特 … / 7 0-3 / 角色 4-7 4 比特 / 层级 8 0-3 / 链路RF 跳数 4-7 4 比特
```

→ **「角色」行在文本流里是 `角色 | 4-7 | 4 比特`**，与「字节号丢失、比特位错列」的现象**完全一致**。

**但像素上并非如此**（见下）。因此：

> **凡涉及合并单元格的表格，PDF 文本流的输出不能直接用于判定字节归属**；
> 必须 400dpi 渲染做像素终裁。**MinerU 转件用 `<td rowspan="N">` 正确还原了合并**，
> 反而比 PDF 文本流更可靠。

这一条同时解释了：为何「朴素解析器会断链」的直觉是对的、而**转件其实没坏**。

## 2. 国网 HDC2.0 表63「站点属性信息格式」（载波 23B）— P59

**锚点**：PDF **P59**

**像素实测**（本图为该表上半部，下半部在次页）：

| 字段 | 字节号 | 比特位 | 字段大小(比特) |
|---|---|---|---|
| **TEI**（占 2 行）| 行1 = **0** / 行2 = **1** | 行1 = **0-7** / 行2 = **0-3** | **12**（合并格，跨两行）|
| **代理 TEI**（占 2 行）| 行1 = **1** / 行2 = **2** | 行1 = **4-7** / 行2 = **0-7** | **12**（合并格，跨两行）|
| 角色 | **3** | **0-3** | 4 |
| 层级 | **3** | **4-7** | 4 |

**要点**：表63 的**字节号列是逐行书写**（0/1、1/2、3、3），**不合并** —— 与表92 用合并单元格**是两种不同表风格**。
这解释了为什么全文存在「无 rowspan 的 `<td>7</td><td>0-3</td>`」形态：那是**逐行书写字节号的正常表**（如「站点3目的TEI」「站点TEI1」），**不是缺陷**。

**与我的构造帧B 逐位对照**（帧B IE 内容 = `23 41 23 21 66 77 88 99 AA BB 00 2A 4E 5A 1E 00 3C 0A 03 78 56 34 12`）：

| 字段 | 像素布局 | 帧B 实际字节 | 解析值 | 一致 |
|---|---|---|---|---|
| 站点 TEI | byte0 bit0-7 + byte1 bit0-3 | b0=0x23, b1 低4=1 | 0x123 = **291** | ✅ |
| 代理 TEI | **byte1 bit4-7 + byte2**（非字节对齐）| b1 高4=4, b2=0x23 | `(0x41>>4)\|(0x23<<4)` = 0x234 = **564** | ✅ |
| 角色 | byte3 bit0-3 | b3=0x21 → 低4=1 | 1 (STA) | ✅ |
| 层级 | byte3 bit4-7 | b3=0x21 → 高4=2 | 2 | ✅ |
| 代理上行接收率 | byte12 | 0x4E | **78** | ✅ |
| 代理下行接收率 | byte13 | 0x5A | **90** | ✅ |
| 最小通信成功率 | byte16 | 0x3C | **60** | ✅ |

> ✅ **帧B 与 PDF 像素逐位一致。**
